# Catalog UI implementation plan: Frequency column + pinned columns

This is a concrete, Amplify-specific implementation plan for two catalog-table features that were already built and verified in the sibling repo `daggerok/SPDR`. It is written for an implementing agent with no access to SPDR or to the conversation that produced this plan — every instruction below is self-contained and points at real code in this repo.

## 0. Architecture note (read this first)

**Amplify has no `app.tsx`.** Unlike SPDR, this repo's entire application — markup, the `<style>` block, and the app logic — lives in one file: `index.html` (currently ~1985 lines). Do not go looking for a separate TypeScript/JSX file. All edits below are edits to `index.html`, plus one file edit to `scripts/update-data.ts` (the Bun data-generation script that produces `api/data.json`).

Concretely, in `index.html`:
- The `<style>` block is lines 36–62.
- The inline app logic lives in `<script type="text/babel" data-presets="typescript">` starting at line 163 and closing at line 1983.
- There is a static placeholder `<thead>`/`<tbody>` in the markup (lines 143–154) with only 3 columns (`#`, `ETF`, `Fund Name`) plus a "Loading…" row. This is only ever seen for an instant before JS runs — the real catalog header/rows are generated entirely by `renderFundsTable()` (`el.tableHead.innerHTML = ...` / `el.tableBody.innerHTML = ...`), so the actual column set to edit is in that function, not in the static markup.

**What this app actually models:** like its siblings, this is an "ETF holdings to Watchlist" app. The **All ETFs** tab is a catalog of Amplify ETFs (ticker, name, NAV, net assets, expense ratio, yields, returns, etc.) built from `api/data.json`, generated by `scripts/update-data.ts` from Amplify's own Firestore data feed. The **Watchlist** tab aggregates holdings of selected ETFs. A shared `<table>`/`#table-head`/`#table-body` pair (inside one scroll container) is reused to render *every* tab — All ETFs, Watchlist, and each selected fund's detail sub-tabs (Overview, Holdings, Performance, Allocations, Distributions, Yields, Price) — each tab calling its own `render*Table()` function that overwrites `el.tableHead.innerHTML`/`el.tableBody.innerHTML`. This matters for section 2 below: any sticky-column CSS must be scoped to classes applied only on catalog cells, never to positional selectors, because the exact same table skeleton renders differently-shaped tables for every other tab.

## 1. Distribution frequency column

### Current state: no such column exists, and no raw cadence field exists in the feed

Checked and confirmed:
- `index.html`'s catalog header (`renderFundsTable()`, `el.tableHead.innerHTML`, lines 778–805) has no frequency/cadence column today.
- The `COLUMN_TOOLTIPS` map (lines 314–373) has no frequency entry.
- Amplify's Firestore feed does **not** publish a distribution-frequency/cadence field anywhere. `scripts/update-data.ts` fetches `funds/{ticker}/distributions/*` documents (`fetchDistributions()`, line 586) and each decoded distribution document only has `exDate`, `recordDate`, `payableDate`, `amount`, `currency`, `type`, `note`, `year` (see `normalizeDistribution()`, line 686). `type` here is the *distribution's own type* (e.g. "Income" / "Capital Gain"), not a per-fund cadence — it is unrelated to what SPDR calls `frequency`.
- The `distributions` subcollection is currently **empty for every fund** in the committed snapshot: `api/data.json`'s `counts` block reports `"distributions": 0` across all 49 funds (confirmed by inspecting `api/data.json` directly), and e.g. `details.DIVO.distributions` is `[]`.

So there is no existing field to "just read" the way SPDR reads `fund.distributions.frequency` from SSGA. The gap to close is: **derive** a coded cadence from the same `distributions` data Amplify's own feed already provides per fund, computed once at data-generation time in `scripts/update-data.ts` (not in the browser, and not from any new external source — this is the same Firestore `distributions` subcollection `fetchDistributions()` already fetches today). The browser then only displays the precomputed string, exactly like it already does for every other catalog metric.

### 1.1 Add a frequency computation to `scripts/update-data.ts`

Add this helper near `normalizeDistribution()` (line 686), reusing the existing `inferYear()` helper (line 812):

```ts
// Derives a sortable distribution-cadence code from this fund's own distribution
// history (same Firestore `distributions` subcollection already fetched above).
// Codes keep a 2-digit numeric prefix so the catalog column sorts meaningfully.
function computeDistributionFrequency(distributions: JsonRecord[]): string {
  const countsByYear: Record<string, number> = {};
  distributions.forEach(event => {
    if (!event || !event.exDate) return;
    const year = String(event.year || inferYear(event.exDate) || '');
    if (!year) return;
    countsByYear[year] = (countsByYear[year] || 0) + 1;
  });
  const years = Object.keys(countsByYear).sort().reverse();
  if (!years.length) return '00 - Unknown';
  const count = countsByYear[years[0]]; // most recent calendar year with data
  if (count === 12) return '01 - Monthly';
  if (count === 4) return '04 - Quarterly';
  if (count === 2) return '06 - Semi-annually';
  if (count === 1) return '12 - Annually';
  return '99 - Irregular';
}
```

In the per-ticker build loop, `detailsByTicker[ticker] = { ... }` (line 501), the `distributions` field is already set from `distributionsDocs.map(normalizeDistribution).filter(Boolean)` (line 511). Capture that into a local variable and add a new sibling field:

## 2. Horizontally pinned catalog columns

### Current state: no pinning exists yet; only the header is sticky (vertically)

Searched `index.html` for `sticky`, `pinned`, `table-scroll`:
- The only existing `sticky` usage is on `<thead id="table-head" ...>` (line 143), which has `sticky top-0 z-20` — this is **vertical** sticky-header-while-scrolling-down behavior only. It is unrelated to horizontal column pinning and must be preserved as-is.
- There is no `#table-scroll` id anywhere yet — the horizontally-and-vertically scrolling wrapper is the unnamed `<div class="max-h-[calc(100vh-245px)] overflow-x-auto overflow-y-auto themed-scroll">` at line 141. It needs an `id="table-scroll"` added so the CSS below can scope to it.
- No column in any table (catalog or otherwise) currently has `position: sticky` applied on a `<th>`/`<td>` for horizontal pinning, and there is no nested-wrapper anti-pattern to fix — this is a from-scratch addition, not a bug fix.

### Real column names/widths to pin

In the catalog (`renderFundsTable()`), the columns to pin are:
- **Use** header: `useHeader()` (lines 451–459) — `<th class="py-3.5 px-4 w-20 text-center" ...>` (already `w-20` = 5rem). Body cell: line 817, `<td class="py-2.5 px-4 text-center">` (currently **no width class** — must gain one).
- **Ticker** header: produced by `sortHeader('Ticker', 'ticker')` (line 782) → `<th class="py-3.5 px-4" ...>` (currently **no width class**). Body cell: line 823, `<td class="py-2.5 px-4 font-mono font-semibold text-blue-600 dark:text-blue-400">${escapeHtml(fund.ticker)}</td>` (currently **no width class**).

All Amplify tickers are short (3–4 letters, e.g. `DIVO`, `IDVO`, `SILJ`), so 5rem is generous and keeps both pinned columns the same width, matching the `Use` column's existing `w-20`.

Do **not** pin the `#` row-index column (`indexHeader()`, lines 447–449) — it must keep scrolling away with the rest of the row, per the shared contract.

### 2.2 Add sticky CSS to the `<style>` block (lines 36–62)

Append this block inside the existing `<style>...</style>` (e.g. right before the closing `</style>` at line 62). Values below were derived directly from Amplify's own tokens already used elsewhere in this file, not copied from SPDR:

- Base row background: the table wrapper is `bg-white dark:bg-slate-800/50` — the pinned cell's own **opaque** base uses solid `#fff` (light) and solid `#1e293b` / Tailwind `slate-800` (dark), which is the un-diluted version of that same token.
- Row hover uses `hover:bg-slate-50 dark:hover:bg-slate-700/30` (on the `<tr>`, see line 815). `bg-slate-50` is already fully opaque (`#f8fafc`) so it can be reused as-is. `slate-700/30` is translucent — pre-blended over the solid `#1e293b` base it resolves to opaque `#243043` (`51,65,85` at 30% over `30,41,59`).
- Selected rows use the existing `.selected-row` class (line 51: light `#eff6ff`, already opaque, reuse as-is; line 52: dark `rgba(30,64,175,.22)`) — pre-blended over the solid `#1e293b` base it resolves to opaque `#1e2e55` (`30,64,175` at 22% over `30,41,59`).

```css
#table-scroll table{border-collapse:separate;border-spacing:0;isolation:isolate}
#table-scroll tbody{position:relative;z-index:0}
#table-scroll tbody tr{position:relative;z-index:0}
#table-scroll .catalog-sticky-col{position:sticky;background:#fff;background-clip:padding-box}
#table-scroll thead .catalog-sticky-col{top:0;z-index:30}
#table-scroll tbody .catalog-sticky-col{z-index:20}
#table-scroll .catalog-sticky-use{left:0;width:5rem;min-width:5rem}
#table-scroll .catalog-sticky-ticker{left:5rem;width:5rem;min-width:5rem;box-shadow:4px 0 6px -6px rgba(15,23,42,.7)}
.dark #table-scroll .catalog-sticky-col{background:#1e293b}
#table-scroll tbody tr:hover .catalog-sticky-col{background:#f8fafc}
#table-scroll tbody tr.selected-row .catalog-sticky-col{background:#eff6ff}
.dark #table-scroll tbody tr:hover .catalog-sticky-col{background:#243043}
.dark #table-scroll tbody tr.selected-row .catalog-sticky-col{background:#1e2e55}
```

`#table-scroll table{border-collapse:separate;...}` is an ID + type selector, so it correctly overrides the Tailwind utility class `border-collapse` (which sets `collapse`) already on the `<table>` element (line 142) regardless of stylesheet injection order, since ID selectors always outrank a single class selector.

`.catalog-sticky-col` must be applied **directly on the `<th>`/`<td>` elements** — never on a wrapper `<span>`/`<div>` nested inside a statically-positioned cell. A sticky element cannot escape its containing block; if the sticky styling were put on an inner wrapper while the actual `<th>`/`<td>` stayed `position: static`, the wrapper would scroll away together with its static parent the moment the parent leaves the viewport, which only becomes visible once you scroll all the way to the right — this is the exact regression the generic checklist warns about, so verify this repo's implementation the same way: scroll the live table fully to the right (in a real or headless browser) and confirm the `Use` and `Ticker` columns are still visible and clickable, not just glance at `scrollLeft = 0`.

### 2.5 Scope check

`.catalog-sticky-col`/`.catalog-sticky-use`/`.catalog-sticky-ticker` are only ever added inside `renderFundsTable()` (the All ETFs catalog). Every other `render*Table()` function (`renderWatchlistTable`, `renderPerformanceTable`, `renderAllocationsTable`, `renderDistributionsTable`, `renderYieldsTable`, `renderPriceTable`, `renderOverviewTable`, `renderSelectedFundHoldings`) must **not** gain these classes — they render a shared `#table-scroll`/`#table-head`/`#table-body` DOM but with entirely different columns, so a positional selector (e.g. `#table-scroll th:nth-child(2)`) would silently misapply pinning there. The CSS in 2.2 above only targets the dedicated classes, never structural/positional selectors, so this is satisfied by construction as long as 2.3/2.4 are implemented as class additions rather than a shared helper that every table calls.

## Handoff summary

Amplify is a single-file (`index.html`) app with no distribution-frequency-equivalent catalog column today and no raw cadence field in its Firestore feed at all — only per-event distribution records (currently empty for every fund in the committed `api/data.json`). The plan adds a `distributionFrequency` field computed once in `scripts/update-data.ts` from each fund's own distribution history, threads it through `FundDetail`/`Fund`/`FundRow`, and surfaces it as a new sortable **Frequency** catalog column between **SEC Yield** and **YTD Return**, matching CSV export. Separately, no column pinning exists yet in this repo (only the existing vertical sticky header) — this is a from-scratch addition, not a regression fix. The plan pins only the **Use** (`left:0`, 5rem) and **Ticker** (`left:5rem`, 5rem) columns directly on their `<th>`/`<td>` elements (never a nested wrapper), using solid pre-blended backgrounds derived from Amplify's own existing hover/selected-row tokens, scoped to new `.catalog-sticky-*` classes applied only inside `renderFundsTable()` so the Watchlist and per-fund detail tables — which reuse the same `#table-scroll` markup — are unaffected.
